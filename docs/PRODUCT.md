# OpenHouse Product

OpenHouse가 사용자에게 **어떻게 동작해야 하는지** 정의하는 제품 기준 문서다.

제품의 비전·문제·MVP 범위는 [`PROJECT.md`](../PROJECT.md), 실제 URL 구조는 [`ROUTES.md`](./ROUTES.md)를 기준으로 한다.

---

## 1. 핵심 사용자

### 참가자

운동 이벤트를 찾고, 내용을 확인하고, 참가 신청과 상태 확인을 하는 사용자.

### 주최자(Host)

체육관을 운영하거나 이벤트를 등록하고 참가자를 관리하는 사용자.

별도 Host 계정을 만들지 않는다. 체육관 owner 권한으로 Host 기능을 제공한다.

---

## 2. MVP에서 검증할 핵심 루프

### 참가자 Golden Path

```text
회원가입 / 로그인
→ 이벤트 탐색
→ 이벤트 상세
→ 참가 신청
→ 신청 완료
→ 마이페이지에서 상태 확인
→ 주최자 승인 후 참가 확정 확인
```

### 주최자 Golden Path

```text
로그인
→ 체육관 등록 또는 내 체육관 진입
→ 이벤트 생성
→ 참가 신청자 확인
→ 승인 / 거절 / 취소 처리
→ 참가 현황 확인
```

MVP의 성공 기준은 기능 수가 아니라 **실제 주최자가 이벤트를 등록하고 실제 참가자가 신청하는 흐름이 끝까지 동작하는 것**이다.

## 3. 정보 구조

핵심 탐색 구조는 다음 네 영역을 중심으로 한다.

- 홈
- 이벤트
- 체육관
- 마이페이지

세부 URL과 redirect는 [`ROUTES.md`](./ROUTES.md)에서 관리한다.

## 4. 회원가입과 프로필

### 원칙

- 가입 진입 장벽을 낮춘다.
- 서비스 이용에 당장 필요하지 않은 정보를 한 화면에서 과도하게 요구하지 않는다.
- 운동 정보와 공개 범위는 프로필에서 보완 가능해야 한다.

### 프로필 목적

프로필은 커뮤니티 장식보다 다음 기능을 우선 지원한다.

- 참가 신청 시 필요한 운동 정보 제공
- 주최자의 참가자 확인
- 공개 프로필/친구 기능(MVP+)의 기반
- 개인정보 공개 범위 관리

실제 저장 필드는 [`DATABASE.md`](./DATABASE.md)를 따른다.

---

## 5. 이벤트 탐색

사용자는 로그인 여부와 관계없이 가능한 범위에서 이벤트를 발견할 수 있어야 한다.

### 목록에서 빠르게 판단할 정보

- 이벤트명
- 종목
- 날짜/시간
- 장소 또는 체육관
- 모집 상태
- 참가비
- 정원/참가 현황(가능한 경우)

### 탐색 방식

- 검색
- 종목 필터
- 지역 필터
- 날짜/빠른 필터
- 모집 상태
- 리스트/캘린더

쿼리 파라미터는 [`ROUTES.md`](./ROUTES.md)를 기준으로 한다.

---

## 6. 이벤트 상세

이벤트 상세는 사용자가 **참가할지 결정하는 화면**이다.

### 반드시 명확해야 하는 것

- 어떤 운동인가
- 언제 하는가
- 어디서 하는가
- 누가 주최하는가
- 누구나 참가 가능한가 / 난이도는 어떤가
- 비용이 있는가
- 무엇을 준비해야 하는가
- 신청 가능한 상태인가

### Primary CTA

모집 중이며 신청 가능한 사용자에게는 `참가 신청`이 가장 중요한 행동이다.

신청 불가 상태라면 버튼만 비활성화하지 말고 이유를 설명한다.

예:

- 모집 마감
- 정원 마감
- 이벤트 취소
- 이미 신청함
- 로그인 필요

---

## 7. 참가 신청

참가 신청은 이벤트 관심등록과 구분한다.

- **관심**: 나중에 다시 보기 위한 저장
- **참가 신청**: 정원과 승인 흐름에 영향을 주는 실제 신청

### 기본 상태

현재 제품 기준 신청 상태:

- `pending` — 승인 대기
- `approved` — 참가 확정
- `rejected` — 거절
- `cancelled` — 취소

DB enum/constraint가 변경되면 [`DATABASE.md`](./DATABASE.md)와 함께 갱신한다.

### 승인 모델

현재 핵심 흐름은 **수동 승인**을 기준으로 한다.

```text
참가 신청
→ pending
→ Host 확인
→ approved 또는 rejected
```

자동 승인 기능을 다시 도입하려면 제품 결정과 DB/QA 기준을 함께 검토한다.

---

## 8. 동행 신청 (MVP+)

운동 친구와 함께 참가할 수 있는 기능이다.

원칙:

- accepted 친구만 선택 가능
- 한 그룹은 동일한 `party_id`로 연결
- 정원 부족 등 실패 시 부분 신청이 생기지 않아야 한다
- 혼자 신청 Golden Path를 복잡하게 만들지 않는다

---

## 9. 체육관

체육관은 이벤트의 장소이자 주최자 신뢰 정보를 제공하는 핵심 Entity다.

### 참가자에게 필요한 정보

- 체육관명
- 종목
- 주소/지역
- 대표 이미지
- 소개
- 시설 정보
- 운영/수업 정보
- 지도자 또는 담당자 정보
- 예정 이벤트

### 주최자 기능

- 체육관 등록
- 체육관 수정
- 내 체육관 목록
- 체육관별 이벤트 관리

세부 필드와 저장 방식은 [`DATABASE.md`](./DATABASE.md)를 따른다.

---

## 10. 이벤트 생성/수정

주최자는 본인이 관리할 수 있는 체육관을 기준으로 이벤트를 생성한다.

핵심 입력:

- 제목
- 설명
- 이벤트 유형
- 종목
- 체육관/주소
- 날짜/시간
- 정원
- 참가비
- 신청 마감
- 난이도
- 방문/준비 안내

권한은 UI 숨김만으로 보장하지 않고 RLS/RPC와 함께 보장한다.

---

## 11. 참가자 관리

Host 참가자 관리의 목적은 복잡한 CRM이 아니라 **현재 이벤트 운영에 필요한 판단을 빠르게 하는 것**이다.

Host가 확인해야 할 핵심:

- 신청자
- 신청 상태
- 신청 당시 운동 정보
- 참가 인원/정원
- 승인 / 거절 / 취소 액션
- 운영자 메모(있는 경우)

MVP에서는 운영 통계 대시보드보다 신청자 관리 흐름을 우선한다.

---

## 12. 마이페이지

별도의 일반 사용자 대시보드와 운영자 대시보드를 중복 구축하지 않는다.

마이페이지를 개인 활동의 중심으로 사용하고, Host 권한이 있는 사용자에게 필요한 운영 진입점을 추가한다.

주요 영역:

- 프로필
- 내 참가
- 관심
- 알림
- 설정
- 문의/신고
- Host 진입(해당 사용자만)

실제 IA는 [`ROUTES.md`](./ROUTES.md)를 따른다.

---

## 13. 관심등록 (MVP+)

용어는 `찜`이 아니라 **관심**으로 통일한다.

- 관심 이벤트 → `event_interests`
- 관심 체육관 → `gym_follows`

관심등록은 참가 신청과 독립적이며 정원에 영향을 주지 않는다.

---

## 14. 알림 (MVP+)

현재 앱 내 알림은 운영 흐름 보조 기능이다.

우선순위 예:

- 참가 신청 상태 변경
- 이벤트 공지
- 이벤트 취소/변경

푸시 알림 고도화는 Beta 범위로 취급한다.

---

## 15. MVP에서 우선하지 않는 것

다음 기능은 핵심 검증 루프를 방해하지 않는 범위에서만 유지/검토한다.

- 친구/공개 프로필의 확장
- 대련 찾기 고도화
- 추천 알고리즘
- 후기/별점
- 결제
- DM/채팅
- QR 체크인
- 고급 운영 통계
- 마켓플레이스

기능이 이미 구현되어 있더라도 **새 개발 우선순위가 자동으로 높아지는 것은 아니다.**

---

## 16. 제품 변경 완료 기준

제품 기능을 변경할 때 다음 질문에 답할 수 있어야 한다.

1. 어떤 사용자의 어떤 문제를 해결하는가?
2. 현재 MVP / MVP+ / Beta 중 어디에 속하는가?
3. 기존 Golden Path를 더 단순하게 만드는가, 복잡하게 만드는가?
4. 어떤 route가 바뀌는가?
5. 어떤 DB/RLS/RPC가 바뀌는가?
6. 성공/실패/빈 상태는 무엇인가?
7. 무엇을 테스트해야 완료인가?

답이 불명확하면 구현보다 요구사항 정리가 먼저다.
