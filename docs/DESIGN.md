# OpenHouse Design & UX

OpenHouse 화면의 **시각·상호작용 원칙**을 정의한다.

제품 동작은 [`PRODUCT.md`](./PRODUCT.md), 실제 화면/URL은 [`ROUTES.md`](./ROUTES.md)를 따른다.

---

## 1. 브랜드 방향

OpenHouse는 스포츠 서비스지만 전형적인 헬스장 예약 앱처럼 보이지 않는다.

핵심 인상:

- Clean
- Community-first
- Modern
- Sporty
- Friendly
- 빠르게 이해되는 정보 구조

브랜드 표현보다 사용자의 다음 행동을 이해시키는 것이 우선이다.

---

## 2. 핵심 UX 원칙

### 모바일 우선

주요 사용자 흐름은 모바일 화면에서 먼저 검증한다.

### 3초 원칙

사용자가 화면에 들어온 뒤 약 3초 안에 다음을 이해할 수 있어야 한다.

- 이 화면이 무엇인지
- 핵심 정보가 무엇인지
- 다음에 무엇을 누르면 되는지

### Primary CTA는 하나를 명확하게

한 화면에 같은 중요도의 행동을 여러 개 경쟁시키지 않는다.

예:

- 이벤트 상세 → `참가 신청`
- 체육관 등록 → `등록하기` / `저장`
- 이벤트 등록 → `이벤트 등록`

### 상태를 숨기지 않는다

불가능한 행동은 단순 disable보다 이유를 보여준다.

예:

- 모집 마감
- 정원 마감
- 승인 대기
- 참가 확정
- 로그인이 필요합니다

### 정보 밀도 조절

첫 화면에는 의사결정에 필요한 정보만 우선 노출하고, 세부 정보는 섹션/상세 영역으로 분리한다.

---

## 3. Navigation

핵심 탐색은 다음을 중심으로 한다.

- 홈
- 이벤트
- 체육관
- 마이페이지

모바일에서는 하단 navigation이 핵심 기능 진입을 방해하지 않아야 한다.

실제 route는 [`ROUTES.md`](./ROUTES.md)를 따른다.

---

## 4. 이벤트 카드

카드는 상세 페이지에 들어가기 전에 빠르게 참가 여부를 판단하도록 돕는다.

우선 정보:

1. 대표 이미지 또는 시각적 식별 요소
2. 이벤트명
3. 종목
4. 날짜/시간
5. 체육관 또는 위치
6. 모집 상태
7. 참가비(있는 경우)

관심 하트는 참가 CTA와 혼동되지 않도록 보조 행동으로 표현한다.

---

## 5. 체육관 카드

우선 정보:

1. 대표 이미지
2. 체육관명
3. 종목
4. 주소/지역
5. 예정 이벤트 또는 추천 이유(필요 시)
6. 관심 상태

관심 하트는 체육관 이름과 자연스럽게 연결되는 위치에 둔다. 카드 전체 클릭과 하트 클릭이 충돌하지 않게 한다.

---

## 6. 관심등록

용어는 **관심**으로 통일한다.

상태:

- 빈 하트 → 관심 미등록
- 채워진 하트 → 관심 등록

원칙:

- 참가 신청과 시각적으로 구분
- optimistic UI 사용 시 실패 rollback/토스트 제공
- 카드와 상세에서 동일한 의미 사용

---

## 7. 이벤트 상세

위에서 아래로 사용자의 의사결정 순서를 따른다.

권장 정보 순서:

1. 대표 정보(제목/종목/상태)
2. 날짜/시간/장소
3. 참가 조건/난이도/정원/비용
4. 설명
5. 준비물/방문 안내
6. 체육관/주최자 정보
7. 참가자 관련 정보(허용되는 범위)
8. CTA

모바일에서 Primary CTA가 긴 스크롤 때문에 사라지는 경우 sticky CTA를 검토할 수 있으나 다른 UI를 가리지 않아야 한다.

---

## 8. Form

### 한 번에 너무 많이 묻지 않는다

회원가입과 등록 Form은 필수 정보와 선택 정보를 구분한다.

### Label 우선

placeholder만으로 필드 의미를 전달하지 않는다.

### 입력 실패

오류는 가능한 한 해당 필드 근처에서 구체적으로 설명한다.

나쁜 예:

`오류가 발생했습니다.`

좋은 예:

`신청 마감일은 이벤트 시작일보다 이전이어야 합니다.`

### 저장 상태

- 저장 중 중복 제출 방지
- 성공 후 다음 위치 명확화
- 실패 시 입력값 보존

---

## 9. Empty / Loading / Error

### Empty

데이터가 없다는 사실과 다음 행동을 함께 보여준다.

예:

`아직 신청한 이벤트가 없습니다.`
`이벤트 찾아보기`

### Loading

화면 전체를 불필요하게 막지 않고, 사용자가 무엇을 기다리는지 알 수 있게 한다.

### Error

데이터 없음과 요청 실패를 같은 UI로 처리하지 않는다.

가능하면:

- 무엇이 실패했는지
- 다시 시도할 수 있는지
- 다른 경로가 있는지

를 제공한다.

---

## 10. 권한 UX

권한이 없는 기능을 단순히 숨기는 것만으로 보안을 해결하지 않는다.

UI는 사용자의 혼란을 줄이는 역할이고, 실제 권한은 서버/RLS/RPC가 보장한다.

예:

- 다른 사람 이벤트 수정 URL 직접 접근 차단
- Host 기능은 owner만 노출
- 민감 정보는 공개 범위에 맞게 표시

---

## 11. 접근성과 기본 품질

- 버튼/링크는 키보드와 스크린리더가 구분 가능해야 한다
- 아이콘만 있는 버튼은 accessible label 제공
- 색만으로 상태를 전달하지 않는다
- 모바일 터치 타깃을 너무 작게 만들지 않는다
- 텍스트 대비를 확보한다
- 이미지에는 의미에 맞는 alt 사용

---

## 12. MVP 디자인 원칙

MVP에서 우선하지 않는다.

- 과도한 animation
- 화려하지만 기능과 무관한 motion
- 불필요한 dashboard chart
- 복잡한 personalization UI
- 여러 단계의 장식성 onboarding

**빠른 이해 + 핵심 흐름 완료 + 오류 예방**이 시각적 완성도보다 우선이다.

---

## 13. 디자인 변경 체크

UI 변경 전:

1. 어떤 사용자 문제를 해결하는가?
2. Primary CTA가 더 명확해지는가?
3. 정보가 너무 많아지지 않는가?
4. 모바일에서 먼저 확인했는가?
5. Loading/Empty/Error 상태를 고려했는가?
6. 기존 카드/Form 패턴을 재사용할 수 있는가?
7. `PRODUCT.md` 또는 `ROUTES.md` 변경도 필요한가?
